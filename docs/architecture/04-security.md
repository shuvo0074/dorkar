# 04 — Identity, Security & Privacy

## 1. Authentication

Phone + OTP only (Stage 1). No passwords.

### Phone normalization

Input accepted: `01XXXXXXXXX`, `8801XXXXXXXXX`, `+8801XXXXXXXXX`,
`008801XXXXXXXXX`, with spaces/dashes/parentheses, and Bengali digits
(`০১৭…`). Output: E.164 `+8801[3-9]XXXXXXXX`. Operator prefixes 013–019 are
accepted; anything else is `INVALID_PHONE`. The same normalizer is the only
path into the system (identity owns it; the web app reuses it from
`@dorkar/contracts` for instant feedback, but the server is authoritative).

### Flow

```mermaid
sequenceDiagram
  autonumber
  participant C as Client
  participant ID as identity
  participant R as Redis (throttles)
  participant PG as Postgres
  participant SMS as SmsProvider

  C->>ID: POST /auth/request-otp {phone, deviceKey?}
  ID->>ID: normalize phone
  ID->>R: check limits: ip, phone, device, global (sliding windows) + resend cooldown
  alt limited
    ID-->>C: 429 RATE_LIMITED (Retry-After) — same shape whether or not account exists
  end
  ID->>PG: INSERT otp_challenges (code_hash = HMAC(pepper, challengeId‖code), expires 5 min)
  ID->>SMS: send "Dorkar code: 123456" (code never logged)
  ID-->>C: 202 {challengeId, expiresAt, resendAfter}

  C->>ID: POST /auth/verify-otp {challengeId, code, device{key, platform, label}}
  ID->>PG: UPDATE otp_challenges SET attempts = attempts+1 WHERE id=… AND consumed_at IS NULL AND expires_at > now() AND attempts < max_attempts RETURNING …
  ID->>ID: constant-time compare HMAC
  alt wrong / expired / exhausted
    ID-->>C: 400 OTP_INVALID (generic)
  end
  ID->>PG: TX: consume challenge; upsert account (by phone); upsert device; create session; issue refresh token (hash stored); audit; outbox(UserLoggedIn / AccountCreated)
  ID-->>C: 200 {accessToken (JWT, 10 min), account, session} + Set-Cookie refresh (httpOnly, Secure, SameSite=Strict, Path=/api/v1/auth)
```

### Tokens & sessions

| Artifact      | Format                                                                                          | Lifetime                          | Storage                                                                                                                |
| ------------- | ----------------------------------------------------------------------------------------------- | --------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Access token  | JWT, `EdDSA` (Ed25519), claims: `sub`, `sid`, `did`, `roles`, `iat`, `exp`, `jti`, `iss`, `aud` | 10 min                            | client memory only                                                                                                     |
| Refresh token | 256-bit random, opaque                                                                          | 30 days sliding, absolute 90 days | **web**: httpOnly cookie; **mobile**: secure storage. Server stores SHA-256 hash only                                  |
| Device key    | 256-bit random generated by client, sent on verify                                              | until revoked                     | web: `localStorage` (risk signal only); mobile (Stage 3): replaced by a hardware-backed keypair with challenge signing |

- **Rotation with reuse detection**: each refresh consumes the token and
  issues a new one in the same transaction (`used_at`, `replaced_by`). Presenting
  an already-used token revokes the whole session (token theft signal) and
  emits a security audit event.
- `POST /auth/logout` revokes current session; `POST /auth/logout-all`
  revokes all sessions; `DELETE /me/devices/:id` revokes a device and its
  sessions.
- Gateway and services verify JWTs locally with the JWKS from identity
  (`/.well-known/jwks.json`), cached; key rotation by `kid`.
- **Immediate revocation at the edge** (ADR-0007): identity publishes
  `SessionRevoked` (logout, refresh-token reuse), `DeviceRevoked`,
  `AccountSessionsRevoked` (logout-all) and `AccountStatusChanged` (ban/suspend).
  The gateway consumes them into a Redis denylist keyed by `sid`, `did` and
  account (`iat` cut-off) that lives one access-token TTL. Measured cut-off
  after logout: ~0.3 s. If Redis is unavailable the check fails _open_
  (signatures are still verified; worst case = the 10-minute TTL). A token
  minted in the same second as a logout-all/ban survives the account cut-off;
  its session is already revoked in identity, so it cannot be refreshed.
- **CSRF**: refresh/logout endpoints are cookie-authenticated → require
  `SameSite=Strict` cookie **and** a custom header `X-Requested-With: dorkar`
  **and** an `Origin` allowlist check. All other APIs use `Authorization:
Bearer` (not ambient), so CSRF does not apply.

### OTP controls (all values in config)

| Control                           | Default                                                           |
| --------------------------------- | ----------------------------------------------------------------- |
| Code length / alphabet            | 6 digits, CSPRNG (`crypto.randomInt`)                             |
| TTL                               | 5 min                                                             |
| Max verify attempts per challenge | 5                                                                 |
| Resend cooldown                   | 60 s                                                              |
| Per phone                         | 5 requests / hour, 10 / day                                       |
| Per IP                            | 20 / hour (NAT-friendly; Bangladesh has heavy CGNAT)              |
| Per device key                    | 10 / hour                                                         |
| Global SMS budget                 | circuit breaker at N/min to cap cost during an attack             |
| Lockout                           | after 3 exhausted challenges in 1 h, phone locked 1 h             |
| Storage                           | HMAC-SHA256 with server-side pepper; never logged, never returned |

Throttles live in Redis; if Redis is unavailable OTP **sending fails closed**
(503) because SMS costs money and abuse is the main risk; verification still
works (it is bounded by the Postgres attempt counter).

Enumeration: request-OTP responds identically for new and existing numbers.
Account suspension is revealed only _after_ a correct OTP.

## 2. Device verification

Device trust is a **risk signal**, never proof of identity.

- `UNTRUSTED` on first login → `TRUSTED` after N days of clean usage or an
  explicit second-factor step (future) → `REVOKED` by user/admin.
- Suspicious-device signals: new device + new network ASN + sensitive action;
  impossible travel; device key reused across many accounts. They raise the
  required assurance (e.g. step-up OTP) rather than block outright.
- Policies such as "high-value transaction requires trusted device" are
  verification policies, not code.

## 3. Authorization model

RBAC for coarse capability + **policy functions** (ABAC-ready) for resource
rules, both centralized in `@dorkar/kernel/authz` and each service's
`application/policies/`.

### Roles → permissions

Roles are stored in identity (`role_grants`) and carried in the JWT. Marketplace
roles are additive: every account is a `MEMBER`; acting as seller/provider is
a _capability_ recorded in profile, not a separate account.

| Role          | Example permissions                                                                                                                              |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `MEMBER`      | `need:create`, `need:manage:own`, `offer:create`, `offer:respond:own`, `listing:create`, `transaction:act:own`, `review:create`, `report:create` |
| `BUSINESS`    | + `sourcing:bulk`, higher limits (limits are policy data)                                                                                        |
| `MODERATOR`   | `moderation:case:read`, `moderation:content:hide`, `moderation:content:restore`, `user:read:basic`                                               |
| `SUPPORT`     | `transaction:read:any`, `user:read:basic`, `dispute:read`                                                                                        |
| `ADMIN`       | `user:suspend`, `category:manage`, `policy:read`, `audit:read`, …                                                                                |
| `SUPER_ADMIN` | `role:grant`, `policy:write`, `verification:nid:read` (break-glass, double-audited)                                                              |

Permissions are granular strings; the role→permission map is data (seeded,
admin-editable, audited). No "is_admin" boolean anywhere.

### Resource policies

```ts
// application/policies/offer-policies.ts
export const canAcceptOffer: Policy<{ actor: Actor; offer: Offer; need: NeedView }> = ({
  actor,
  offer,
  need,
}) =>
  need.requesterId === actor.id && offer.awaitingPartyIs('BUYER')
    ? allow()
    : deny('NOT_OFFER_RECIPIENT');
```

- Use cases call `authorize(policy, ctx)` before any mutation; denial →
  `403 FORBIDDEN` (or `404` when existence itself must not leak, e.g. another
  user's draft need — prevents IDOR enumeration).
- Every query of user-owned data is scoped by actor in the repository method
  signature (`findByIdForRequester(id, actorId)`), so forgetting a check
  returns nothing rather than someone else's data.

## 4. Security controls checklist (OWASP ASVS L2 / API Top 10)

| Risk                    | Control                                                                                                                                                                 |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Injection (SQL)         | Kysely parameterized queries only; raw SQL only via tagged `sql` template; lint bans string-concatenated SQL                                                            |
| XSS                     | React escaping; no `dangerouslySetInnerHTML` (lint); user text stored raw, rendered as text; strict CSP from gateway; `X-Content-Type-Options`                          |
| CSRF                    | bearer tokens for APIs; refresh cookie SameSite=Strict + custom header + Origin check                                                                                   |
| SSRF                    | services never fetch user-supplied URLs; media is uploaded directly to object storage via presigned URLs; outbound HTTP via allowlisted client                          |
| BOLA / IDOR             | actor-scoped repositories + policy checks; UUIDv7 IDs (not guessable sequences — still never relied on for security)                                                    |
| Broken auth             | OTP controls above; short JWT; rotation + reuse detection; logout everywhere                                                                                            |
| Mass assignment         | Zod request schemas are `strict()` (unknown keys rejected); explicit command objects; response DTO mappers                                                              |
| Excessive data exposure | response schemas validated on output; no generic serializers                                                                                                            |
| Rate limiting / abuse   | gateway global + per-route limits; per-actor business limits (needs/day, offers/day) as policies                                                                        |
| Race conditions         | row locks / guarded updates / unique constraints / EXCLUDE constraints; idempotency keys                                                                                |
| Replay                  | idempotency keys; single-use OTP; refresh rotation; JWT `jti` + short exp                                                                                               |
| File upload             | presigned PUT with size cap & content-type condition; server-side magic-byte sniffing; re-encode images (strips EXIF/GPS); ClamAV scan job; private bucket, signed GETs |
| Privilege escalation    | role grants only via `role:grant` permission, audited; JWT roles re-validated on refresh                                                                                |
| Secrets                 | env from secret manager / encrypted files (SOPS) — never in git; `.env.example` only                                                                                    |
| Logging                 | pino redaction of `authorization`, `cookie`, `otp`, `code`, `phone`, `nid*`, `token*`; phones logged as salted hash                                                     |
| Dependencies            | `pnpm audit`, Dependabot/Renovate, `osv-scanner`, Trivy on images                                                                                                       |
| Transport               | TLS everywhere, HSTS; internal traffic on private network                                                                                                               |

## 5. Threat model (STRIDE, top items)

| Asset / flow     | Threat                                 | Mitigation                                                                                       | Residual                         |
| ---------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------- |
| OTP request      | SMS pumping / toll fraud (cost attack) | multi-key throttles, global SMS budget breaker, BD-only numbers, CAPTCHA step-up after anomalies | medium — monitor SMS spend alert |
| OTP verify       | brute force (10⁶ space)                | 5 attempts/challenge, challenge lockouts, HMAC w/ pepper                                         | low                              |
| Refresh token    | theft via XSS                          | httpOnly cookie, CSP, rotation + reuse detection                                                 | low                              |
| Session          | hijack from stolen device              | device revoke, logout-all, suspicious device signals                                             | medium                           |
| Offer acceptance | double acceptance under concurrency    | row lock + guarded update + idempotency                                                          | low                              |
| Bidding          | sniping, shill bidding, race           | anti-snipe extension, owner can't bid, linked-account heuristics, row lock                       | medium (shill)                   |
| Listings/needs   | spam, scams, prohibited items          | per-user limits, verification policies per category, reports, moderation queue, keyword rules    | medium                           |
| Contact info     | phone harvesting                       | numbers never shown by default; messaging in-app (Phase 2)                                       | low                              |
| NID data         | breach / insider access                | prefer provider; encrypted vault, separate role, break-glass access audited, retention           | low                              |
| Admin panel      | privilege abuse                        | granular permissions, all actions audited, 4-eyes for policy/role changes (Phase 2)              | low                              |
| Reputation       | review manipulation                    | reviews only from completed transactions, one per party, multiple signals, anomaly detection     | medium                           |
| Event bus        | forged events                          | private network, Redis ACL per service, producers identified in envelope                         | low                              |

## 6. Privacy & data protection

Principles: data minimization, purpose limitation, separation of sensitive
data, explicit DTOs, auditable access. Designed to align with Bangladesh's
data-protection framework as it evolves (and GDPR-style practices).

| Data                         | Purpose                     | Where                                     | Access                                                       | Retention                                                    |
| ---------------------------- | --------------------------- | ----------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| Phone number                 | login, SMS                  | identity only                             | identity service; support via masked view (`+88017•••••123`) | life of account + 30 days                                    |
| OTP                          | login                       | identity (hash)                           | nobody                                                       | 24 h then purged                                             |
| IP address                   | abuse prevention            | identity/gateway as salted hash           | security staff                                               | 90 days                                                      |
| Device key                   | risk signal                 | identity (hash)                           | identity                                                     | until revoked + 90 days                                      |
| Profile (name, avatar, area) | marketplace trust           | profile                                   | public subset via DTO                                        | life of account                                              |
| Delivery address             | fulfilment                  | transaction (snapshot)                    | the two parties                                              | 180 days after completion, then redacted                     |
| NID                          | regulatory/high-value trust | provider; if unavoidable, encrypted vault | break-glass only                                             | policy-defined (e.g. 1 year after last use), hard delete job |
| Messages                     | coordination                | messaging                                 | participants + moderators on report                          | 1 year                                                       |
| Audit logs                   | security, accountability    | each service                              | auditors                                                     | 2 years (partition drop)                                     |

- **Account deletion**: `AccountDeletionRequested` event → each service
  anonymizes or deletes its data per the table above; transactional records
  needed for legal/accounting are retained with the user pseudonymized.
- NID raw data is never returned by any API. Clients receive only
  `{ nidVerified: true, verifiedAt }`.
